# ADR 0004: The admin pages' building blocks: state badges, banners, data tables, confirming and More actions

## Status

Accepted (2026-11-25, by the owner). The implementer's calls, done in 0.5.0.

## Context

RadioArchive's first admin pages (its ADR 0027: Recorders and Settings) found that ArchiveUx 0.4.1 had no badge for a state in words, no table, no way to ask before a destructive action, and no class for an alert (section 4 described an alert's look and each app drew it). Its recent calls (RadioArchive's ADR 0023) had built a "More actions" button of their own for phones. Each page drew stand-ins from tokens only: the Warning badge as the Delayed badge's pairing, OK as a saved message's, a recorder's systems as page rows, the retention question as an inline panel with a danger button, alerts as the `--warn-bg` fill. Its ADR 0027 ends: "If these recur (the Talkgroups and Units pages will want a state badge and a table), they belong in ArchiveUx." They recur: Talkgroups, Units, Systems, Accounts and the Audit log are next. PagerArchive's admin pages (clients, users, aliases) draw their own tables and inline confirmations, which the rules below follow.

ADR 0002's rule holds: what only one app uses stays in it. These are generic, both apps' admin pages have them, and RadioArchive may make no tokens of its own (its R80), so they come here.

## Decisions (the implementer's)

1. **Five building blocks, as Svelte components with classes where a class is enough.** `.state-badge` and `.banner` are classes in `base.css` (an app can write the markup by hand, as with `.live-badge`), with `StateBadge` and `Banner` as thin components. `DataTable`, `Confirm` and `MoreActions` hold behaviour (sorting, focus, Escape), so they are components only. Svelte 5 in plain JavaScript with JSDoc, shipped as source, like the frame (ADR 0002, decision 7). Sorting is in `table.js`, apart from the component, so a server can follow the same order and the tests hold its cases.
2. **One new token, `--danger-soft`, the soft fill of an error**, as `--warn-bg` is a warning's; its text is the existing `--danger-text`. A soft fill keeps the four states and three tones one family (soft fill and its own ink), where `--danger` with `--danger-fg` would be as loud as a danger button and look like one. Harbour's value is its Emergency label's fill (`#fde4e1`, `#4b1f1b`), already in the look; Console's is a light and a dark red tint (`#fbe4e4`, `#3a1515`) like its `--warn-bg`. Measured 5.66 to 8.36. **No existing token changes**, and no other token is added: sizes reuse `--badge-*`, `--label-min`, `--field-wide`, `--dialog-width`, `--measure`.
3. **State badges: four states, the word is the app's.** `ok` (`--accent-soft-fg` on `--accent-soft`, a saved message's pair), `warning` (`--warn-fg` on `--warn-bg`), `error` (`--danger-text` on `--danger-soft`) and `neutral` (`--muted` in a `--control-border` outline, no fill) for off, hidden, retired and never seen, which are neither good nor bad and shouldn't look like either. Sized and cased as the priority labels, so Console writes them in capitals. The words default to OK, Warning and Error, but the rules ask for the state's own word ("Quiet", "Deaf"), because that's what an admin acts on. Console's OK is grey, its accent being ink: the word carries it, as everywhere.
4. **Banners: the alert, as a class, in three tones, with no edge.** `.banner[data-tone=warning|error|info]`: `warning` is the alert section 4 already describes, so the owner's decision of 2026-11-20 (no edge) applies to all three. `error` for a page that can't do its job, `info` (`--accent-soft`) for a fact worth saying once. A leading icon per tone, hidden, so the words say the tone. Named `.banner`, not `.alert`: both apps already have local `.alert` classes, and a global one in `base.css` would reach into them. A role only when it appears after something happened (`alert`, or `status`), not for one there when the page opens, which would be read out on every load.
5. **Data tables: sortable headers, an actions column, and cards when narrow.**
   - Sorting is client-side by default, because an admin table is short (hundreds of talkgroups, not millions of calls); `sortRows={false}` hands it to the server for a paged one. Headers are buttons inside `th` with `aria-sort` on the sorted one only, plus a polite announcement, because screen readers announce `aria-sort` changes unreliably. A column can sort descending first (Last heard, Calls). Empty values go last both ways, so "Never" stays at the foot whichever way Last heard is sorted.
   - **Narrow is a stack of cards, not a sideways scroll.** At 375 px a five-column table either scrolls (the row's name and its actions fall apart off-screen) or squashes; a card per row keeps the name, each value under its label and the actions together. It follows the table's **own width** (a container query at 40rem), not the screen's, so a table in a narrow card stacks too. The header row hides, so the sorting moves to a **Sort by** select. Each cell keeps its explicit table role (`role="table"`, `row`, `cell`, `rowheader`), because some browsers drop a table's semantics when its cells are drawn as blocks; the label inside each cell is what a screen reader hears in place of the hidden header. `stack="never"` scrolls instead, for a wide log.
   - The actions column's header is for screen readers only ("Actions"), and each action's name names its row.
6. **Confirming: inline by default, a modal dialog when asked.** Both apps already ask inline (PagerArchive's Deactivate, RadioArchive's retention, the basket's Clear), next to what's asked about, with nothing covering the page, so that is the default. `modal` gives a `<dialog>` with `showModal` for when the question would otherwise be off-screen. The question is the heading; the confirm button says the action and is a danger button, Cancel after it, as both apps have it. Inline, the heading takes the focus so the question is read before the buttons; in the dialog Cancel does, so a stray Enter never confirms. The focus returns to whatever asked. An async `onconfirm` holds both buttons and shows a failure in the panel rather than closing it.
7. **More actions is a disclosure, not an ARIA menu.** A menu role promises arrow keys, typeahead and focus rules, and moves screen readers into a mode where links and buttons behave differently; a disclosure of plain buttons is Tab and Enter, as RadioArchive's recent calls already do it. It is a popover under the button (RadioArchive's recent calls open theirs inline under the row, which only a list can do; a table row or a card needs it to float). Choosing an action closes it and returns the focus to the button, so the focus never falls to the page, and a `Confirm` that opens after takes the focus and gives it back to the same button.
8. **New pairs, from existing tokens and `--danger-soft`**: `state-*`, `banner-*`, `table-*`, `confirm-*`, `more-*` (rules, section 4). The contrast check now makes 976 measurements, all passing; the lowest new one is 3.36, a control's border on a hovered row in Harbour light. `contrast/findings.json` stays empty.

## PagerArchive and RadioArchive are unaffected

Every existing token keeps its value in both looks and both themes, and no existing rule in `base.css` changes. 0.5.0 adds one token (`--danger-soft`), two classes whose names neither app uses (`.state-badge`, `.banner`), five components, `table.js` and five icons. Moving from 0.4.1 needs no change in either app.

## Consequences

- RadioArchive's admin pages replace their stand-ins: the recorders' Warning and OK badges with `StateBadge`, the disk warning and "Couldn't reach the server" with `Banner`, the retention question with `Confirm`, and the coming Talkgroups, Units, Systems, Accounts and Audit log pages build on `DataTable` with `MoreActions`. Its recent calls may keep their inline More actions.
- PagerArchive can move its admin tables, its inline Deactivate question and its backup and upgrade alerts (`.banner`, the warning tone, draws them as they are) when it chooses.
- The owner may change any of decisions 2-7 after the demo; the classes and props are new, so nothing depends on them yet.
